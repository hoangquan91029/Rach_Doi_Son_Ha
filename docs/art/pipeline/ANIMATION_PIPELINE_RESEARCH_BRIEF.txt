ROLE
You are a Senior Technical Animation Director and 2D RTS Art Pipeline Engineer.
Your job: DESIGN the animation production pipeline for a browser-based historical
2.5D RTS, then PROVE it on a small pilot. Do NOT mass-produce frames. Do NOT write
a generic animation tutorial. Challenge the current plan instead of agreeing with it.

1. HARD CONSTRAINTS (already decided)
- Browser game (Chrome/Firefox/Edge, WebGL). Modes: single-player vs AI, online 1v1.
- Simulation is authoritative. Animation is client-side visual only. Damage/hits
  never depend on which frame the browser displayed.
- Final look: finished illustrated characters as frame-by-frame sprites. Forbidden
  in shipped art: primitive shapes, visible paper-doll limb rotation, debug art,
  inconsistent AI frames. Primitives are allowed only as internal guides.
- Working assumption of 8 directions for humanoids: you must justify or change it.
- Units: Villager, Spearman, Firearm infantry, King, General (premium historical
  identity; General death = match loss), Cavalry, Artillery + crew, Supply wagon,
  Ships. The pipeline must scale to dozens of units.
- Inspect the repository FIRST. Keep the existing engine unless you find hard
  evidence it cannot support the pipeline.

2. DIAGNOSIS OF THE CURRENT FAILURE (observed in current outputs)
a. The image model is deciding body geometry. In frames that should be opposite
   halves of the walk cycle (e.g. F1 vs F5), the same leg stays planted and the
   arms swing the same way.
b. The reference set mixes three camera angles: canonical bust (frontal, head down,
   one shoulder cropped), generated full-body frames (3/4 view, head turned), and
   the 2D rig mannequin (frontal). The model invents the difference.
c. The part-based diagnostic showed head+torso as one frozen copy with only arms
   swapped, and hands clipping into the tunic skirt. This is the paper-doll failure.
d. Left/right is ambiguous: the brief uses anatomical LEFT/RIGHT, the rig uses
   NEAR/FAR and SCREEN-LEFT/RIGHT. Anatomical left lands on a different screen side
   in each of the 8 directions.
e. The sash knot and tails are asymmetric, which affects mirroring.

3. HYPOTHESIS TO TEST (not to assume)
Pose comes from deterministic data. AI only does appearance.

  approved full-body neutral identity sheet (game camera)
  -> 3D proxy mannequin (humanoid rig + walk clip) rendered from the exact game camera
  -> per-frame guide pack: silhouette mask, depth, normal, LIMB-ID COLOR MAP
     (fixed color per limb, anatomical L/R encoded in color, never in words),
     foot-contact markers, root/pivot
  -> constrained image-to-image repaint (identity reference + guides, low strength)
  -> automated validation -> retry/reject
  -> crop/normalize -> atlas -> manifest -> runtime

The existing hidden-joint 2D rig: decide exactly where it belongs (pose guide /
landmark set / nowhere). Hypothesis: do not rotate cut-out limb textures.
You MUST compare these alternatives and score them with evidence:
(1) independent per-frame generation, (2) runtime 2D skeletal rig, (3) 2D rig baked
to frames, (4) 3D rig pre-rendered to 2D (incl. painterly shading and paint-over),
(5) hybrid. You may conclude the hypothesis is wrong.

4. RESEARCH (targeted, only what changes a decision)
- RTS references: Age of Empires / II / DE, StarCraft / Remastered, plus better
  examples if you find them (pre-rendered 3D-to-sprite RTS, atlas practices).
  Per game: sprite or 3D, authoring method, directions, frame counts, mirroring.
- AI tooling: pose/depth conditioning (ControlNet-style), reference/IP-Adapter-style

- Prefer official docs, developer talks, GDC, postmortems. Label forum posts as

5. PILOT BEFORE SCALE (core of the task)
Pilot: Villager walk. Pick the single direction that makes leg phase easiest to
verify (likely pure side view) and justify it. Start with F0 (left contact) and
F4 (right contact) only.
Step A: write the coordinate spec first: game camera (elevation, projection,
  canvas size, pivot), direction -> screen-side mapping of anatomical left/right
  for all 8 directions, and a phase table (frame -> support leg -> expected foot
  positions).
Step B: generate the guide packs; verify programmatically that limb-ID maps differ
  as expected between F0 and F4.
Step C: at least 10 repaint attempts per frame; record the pass rate of each
  automated check.
Step D: only if F0/F4 pass the gate, continue to the full 8-frame cycle, then a
  second direction, then mirrored directions. Define numeric gate thresholds and
  an image budget before the first gate, and justify them.
If the pilot fails, report it honestly and propose a fallback ladder (stronger 3D
shading + paint-over, hand paint-over on key poses, fewer AI-driven frames).
Never loosen thresholds to make it pass.

6. VALIDATION SYSTEM (design and implement what is automatable)
Canvas size, alpha, pivot, bbox; character height; head position; support-foot
lowest point vs guide and no sliding across frames; IoU against guide silhouette;
segmentation of the result vs the limb-ID guide (leg-phase check); color drift;
identity similarity vs canonical (face, hat, sash); frame-to-frame difference;
duplicate/missing frames; loop closure F7 -> F0. State what cannot be automated
and requires a visual audit. Produce a contact sheet and a looping preview
(GIF/APNG/webm) per animation. A parent-agent visual audit is the final gate.

7. DELIVERABLES
(a) Decision report: executive conclusion; score table of the 5 options on visual
    quality, consistency, animation quality, production speed, AI compatibility,
    8-direction scalability, web performance, memory, historical fidelity;
    KEEP / MODIFY / ABANDON verdict on the current rig with scores.
(b) Specs: coordinate spec; walk cycle (8 vs 12 frames, timing, contact/down/
    passing/up, foot lock, root motion handled by the simulation with sprites
    carrying no world translation, fixed ground pivot); direction policy
    (4 / 5+mirror / 8 / 16) with mirroring rules per unit class including
    asymmetric items; frame budget per animation (min / recommended / premium);
    FPS per action; simulation-event vs animation-event architecture; turning,
    transitions, death policy.
(c) Scale math with formulas: LOW / MEDIUM / HIGH roster -> source frames, atlas
    count, GPU memory (RGBA x4, mipmaps), download size, staged loading, animation LOD.
(d) Tooling: directory structure, deterministic naming, manifest schema with a
    concrete example (unit, archetype, animation, direction, frames, durations,
    pivot, events, loop, mirror source, atlas rect), script list.
(e) Archetypes and per-unit strategy: Villager, infantry, firearm infantry,
    King/General (what is shared vs what stays unique), cavalry, artillery,
    supply wagon, ships. Different categories may use different pipelines.
(f) Risk register with mitigations, and a roadmap with gates.
(g) FINAL DECISIONS: USE / DO NOT USE / KEEP / CHANGE / FIRST THING TO BUILD /
    DO NOT SCALE PRODUCTION UNTIL.
