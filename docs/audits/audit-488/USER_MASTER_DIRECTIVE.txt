# PART II — EVIDENCE-BASED AUDITING

## 3. Anti-hallucination rules

Every subagent must distinguish between:

**VERIFIED**

Directly confirmed from repository contents, existing assets, executable commands, or real test results.

**DOCUMENTED_ONLY**

Claimed in project documentation but not independently verified.

**INFERRED**

Reasonable technical interpretation supported by available evidence.

**PROPOSED**

A future architectural recommendation.

**UNKNOWN**

Not enough information to determine.

**FAILED**

A specific test or validation did not pass.

Never treat a proposal as an implemented feature.

Never treat a document's completion claim as proof that the feature works.

Never describe an asset as visually approved unless it was actually inspected.

Never claim successful tests that were not executed.

Never invent:

- File paths
- Classes
- Modules
- Functions
- Assets
- Animation frames
- Framework capabilities
- Tool outputs
- Test results
- Benchmark results
- Historical research sources
- Model availability

## 4. Mandatory evidence format

Important audit findings must contain:

- Claim
- Evidence status
- Exact file path
- Function/class/symbol where applicable
- Line range or relevant source location where practical
- Verification command or inspection method
- Actual observed result
- Remaining uncertainty

Example:

Claim:

"Villager South Walk has a completed eight-frame sequence."

Evidence:

`assets/source/units/villager/walk/s/`

Verification:

Inspect frame files, metadata and preview.

Result:

VERIFIED only if the complete sequence exists and can be inspected.

Otherwise:

DOCUMENTED_ONLY, PARTIAL, or UNKNOWN.

Do not fabricate evidence to fill gaps.

## 5. Source hierarchy

Use the following evidence priority:

1. Executed tests and observed runtime behavior
2. Actual repository code and assets
3. Verified generated output
4. Current project specifications
5. Official technical documentation
6. Verified external technical research
7. Reasoned engineering assumptions

When two sources disagree, record the contradiction and resolve it explicitly.

Do not silently rewrite requirements to match current implementation.

# PART VI — DESIGN A REUSABLE SPRITE PRODUCTION FRAMEWORK

## 12. Separate five different concerns

Do not mix these concepts.

### A. CHARACTER IDENTITY

Defines how a character looks.

Examples:

- Face
- Clothing
- Body proportions
- Historical equipment
- Color palette
- Material
- Headgear

### B. MOTION DEFINITION

Defines how the character moves.

Examples:

- Walk cycle
- Run cycle
- Attack motion
- Foot-contact phases
- Arm swing
- Weight transfer

### C. DIRECTIONAL PROJECTION

Defines how the character is illustrated from different gameplay directions.

### D. FINAL FRAME PRODUCTION

Produces finished illustrated 2D PNG frames from the approved identity and pose references.

### E. RUNTIME ANIMATION

Displays the correct sprite frame in response to the game simulation.

Each layer must have an explicit interface.

A motion definition must not contain the face or clothing identity of a particular historical leader.

A character identity must not require rewriting the entire walk-cycle specification.

## 13. Reusable animation archetypes

Research and design reusable motion families.

At minimum:

**HUMANOID_GENERIC**

Villagers and suitable ordinary humanoid characters.

**HUMANOID_SPEAR**

Spearmen and polearm infantry.

**HUMANOID_FIREARM**

Arquebusiers and musketeers.

**COMMANDER**

Kings and Generals.

**CAVALRY**

Horse and rider.

**ARTILLERY_CREW**

Gunners and loaders.

**SUPPLY_WAGON**

Cart, driver and draft animal where appropriate.

**SHIP**

Directional vessel movement and naval combat animation.

Motion planning should be reusable.

Final artwork should preserve unique equipment and visual identity.

Do not assume every archetype can reuse the exact same finished frames.

## 14. Character identity locking

For every character, establish an approved canonical reference.

Require:

- Canonical image
- Character specification
- Direction conventions
- Anatomy proportions
- Clothing specifications
- Color/material constraints
- Equipment constraints
- Lighting specification
- Shadow specification
- Allowed deviations
- Forbidden deviations

Use image references in subsequent generation calls whenever available.

Do not generate each frame from unrelated natural-language descriptions.

Avoid character identity drift.

## 15. Reusable generation specifications

Create structured generation instructions for:

- Canonical character
- Eight-direction reference sheet
- Walk keyframes
- Run keyframes
- Attack keyframes
- Action-specific keyframes
- In-between frames
- Frame repair
- Clothing correction
- Background removal
- Transparency correction
- Atlas export

Separate:

**Invariant instructions**

Character identity, light, materials, style and camera.

from:

**Variable instructions**

Direction, pose, motion phase and equipment interaction.

Avoid long one-off prompts that agents cannot reuse.

# PART VII — VILLAGER WALK CYCLE: FIRST QUALIFICATION CASE

## 16. Audit the existing Villager

Locate the current Villager source assets.

Determine the true current state.

Do not assume:

- The full body is finished
- Both legs are correctly reconstructed
- The current rig works
- The walk cycle is approved
- All eight directions exist

Inspect the real outputs.

Identify what should be preserved and what should be replaced.

## 17. Correct walk-cycle biomechanics

Create a clear walk specification.

Recommended initial key phases:

1. Left contact
2. Left weight acceptance
3. Right passing
4. Left push-off
5. Right contact
6. Right weight acceptance
7. Left passing
8. Right push-off

Validate:

- Anatomical left/right limb identity
- Contact leg
- Supporting leg
- Swing leg
- Foot placement
- Root movement
- Hip displacement
- Body bob
- Counter-swing of arms
- Clothing deformation
- Loop continuity

Important:

Screen-left and anatomical left are not always the same.

Never use screen coordinates alone to identify anatomical legs.

Support-leg correctness must be checked from the actual motion, not inferred from filenames.

## 18. Two-keyframe qualification gate

Before completing the full walk cycle, generate and validate two opposing contact poses:

**POSE A:** Left foot contacts forward.

**POSE B:** Right foot contacts forward.

Both must retain:

- The same character identity
- The same perspective
- The same clothing design
- The same lighting
- The same body proportions
- The same source-art quality

If both opposing poses cannot be generated correctly, do not proceed to all eight directions.

Diagnose whether the failure comes from:

- Incorrect pose specifications
- Insufficient image control
- Ambiguous body landmarks
- Occluded clothing
- Unsupported image-generation capabilities
- Incorrect reference images

Do not repeat failed generation indefinitely.

Escalate to a different controlled 2D editing technique when required.
