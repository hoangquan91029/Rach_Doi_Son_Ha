## Proposed authority and mandatory-read architecture

PROPOSED: use `docs/PROJECT_STATE.md` for current state and explicit blockers, `docs/PROJECT_ROADMAP.md` for full requirements and gates, and `docs/NEXT_STEPS.md` for finite next work. Put their mandatory read order in AGENTS. Retain root NEXT_STEPS/PROJECT_STATUS and docs/PROJECT_PLAN as thin compatibility links with historical snapshots preserved. A compatibility link must say whether it is current navigation or historical evidence.

PROPOSED read sequence:

1. Inspect Git status and mandatory authority index; identify changed files and each worker's ownership.
2. Read PROJECT_STATE, PROJECT_ROADMAP and docs/NEXT_STEPS; name active blocker and distinguish local/source/candidate/public scope.
3. Read only applicable pure2D/movement/review directive and actual referenced order/claim/receipt handles. Avoid rereading hundreds of historical runs or duplicated entrypoints.
4. Before authoring, resolve canonical identity, selected direction/job, exact reference order, required masks/guide custody, available tools and finite claim state. An OPEN text plan is insufficient call permission; unknown durable claims cannot be reset on elapsed time.
5. Before validation, identify exact artifact and promised observable outcome. Before release, inspect current live handles and preservation guards; historical receipts do not close live guards.

PROPOSED precedence: direct latest user scope and applicable instructions; current requirements/authority index; actual source/assets and exact scoped executed observations; historical evidence; external primary-source research; inference/proposals. Requirements define intended behavior, while observed source/runtime establishes actual behavior. Neither replaces the other. Record disagreement explicitly rather than calling a proposed requirement implemented.

PROPOSED documentation schema: each mutable authority document includes scope, last reviewed checkpoint/date, owner, supersedes links, evidence links, open gates and next authorized action. Each important status row includes evidence label, artifact identity/hash where available, exact source location, check command/method, observed result and remaining uncertainty. Receipt JSON/JSONL should distinguish authored/selected/reviewed/installed/public and retain failures, claims and correction budgets. Human-readable state should derive from these records when practical, with guarded manual interpretation for motion acceptance.

PROPOSED preflight checks: verify mandatory paths exist, detect superseded documents marked current, validate identity/order schemas and pinned references, detect duplicate slot claims, require exact test/artifact scope, and flag unsupported completion language. These checks are fallible aids: passing schemas, JSONL parsing or mandatory-read acknowledgements cannot guarantee comprehension, natural motion, correct supporting-leg exchange, final acceptance or deployment readiness.

PROPOSED immediate edits by root: quarantine the stale 3D recommendation; update production README with restored master custody, target-first reference contract and implemented484 cache limits; keep roster performance and opposite-contact qualification open; centralize continuation status without rewriting retained raw history. Do not turn this report into new art-call, install, browser or release authorization.
